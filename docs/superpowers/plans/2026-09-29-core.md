# @sweep/core (session A) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Implement `@sweep/core`: the guide model, Zod schema and generated JSON Schema, the parser and validator for both containers (every §3.6 code, with line and column), the engine (§4), `diffGuides`, `migrateProgress`, API DTO types, and `sweep validate`.

**Architecture:** `@sweep/core/parse` runs a phased pipeline over a virtual file map: text → container split → YAML → structure (Zod) → identity/reference checks → normalize → graph and window checks → Markdown body and prose checks. Every phase emits `Issue`s located through one YAML-path locator. The main entry `@sweep/core` holds pure engine functions over `(Guide, RunProgress)`, built on a memoized structure index. The parser reuses that index for its window checks. The CLI (`src/cli/`) is the only I/O.

**Tech Stack:** TypeScript 6 (ESM, `module: nodenext`, `.js` import extensions), Vitest 5, `yaml` 2.9, `zod` 4.6, `mdast-util-from-markdown` 2 (+ `@types/mdast`), `ajv` 8 (dev only, to check the generated JSON Schema).

**Spec:** `docs/superpowers/specs/2026-09-28-sweep-design.md` (§2–§4, §6.2 for DTOs, §8, §9). Also read `CLAUDE.md`, `packages/core/CLAUDE.md` and `docs/adr/` before any task.

## Review Focus

These inputs are implied by the spec but easy to miss. Each is pinned by a test in the task named.

1. **Files from other tools:** CRLF line endings, a UTF-8 BOM, `---` fence lines with trailing spaces, and no final newline must give the same model and the same line numbers as a clean LF file (Task 4, Task 11).
2. **Plain-text fields written as YAML numbers or booleans** (`game: 1942`, `title: 2048`, `name: true`) are accepted as their source text, not rejected as `type` errors (Task 6).
3. **`#` lines inside code in a `.md` walkthrough** (``` and ~~~ fences, indented code) neither split sections nor raise `md-heading` (Task 11).
4. **Stored progress that no longer fits the guide** (unknown IDs, a cleared group ID, a pin on a group or a cleared or unknown leaf, task state stored under a section ID) is ignored without throwing (Task 13, Task 14).
5. **Non-linear and forced play:** clearing a locked leaf, `until` cleared before `from` was reached, and reopening a cleared leaf all follow §4.4 and §4.6 exactly (Task 14, Task 16).

## Design decisions (binding for every task)

These fill gaps the spec leaves open. Implementers follow them. Reviewers check them.

### Parser input and output

- `parseGuide(files: GuideFiles): ParseResult` with `type GuideFiles = Record<string, string | Uint8Array>`. This widens the spec's `Record<path, string>` so the server and CLI can pass raw bytes: bytes get a strict UTF-8 decode (`encoding`) and an exact byte-size check (`too-large`). For string input, the byte length is computed by hand, and a lone surrogate is an `encoding` error.
- `ParseResult.guide` is set **only when there are no errors**. Warnings don't block.
- `guideFileName(uploadName: string): 'guide.yaml' | 'guide.yml' | 'guide.md' | null` maps an upload or CLI file name to its virtual name by extension (case-insensitive). The server and CLI both use it.
- Issues are returned sorted by `(line ?? 0, column ?? 0)`, stable. `Issue.file` is the virtual name (`guide.yaml`, `guide.md`, …) or `null` for `no-root-file`.
- Text preprocessing, in order: size check → decode → strip BOM → convert `\r\n` and lone `\r` to `\n`. Line numbers are unaffected.

### Phases and gating

1. **Text:** `no-root-file`, `too-large`, `encoding`. Any error stops.
2. **Container:** for `.md`, split the front matter. `md-front-matter` stops.
3. **YAML:** `yaml-syntax` stops. Then `format-version`, which also stops (a different version may be a different format).
4. **Structure (Zod):** `required`, `type`, `id-format`, `limit`, `no-leaves` (top-level `sections: []`), plus warnings `unknown-key` and `overview-long`. Any error stops.
5. **Identity and references:** `id-reserved`, `id-duplicate` (sections and tasks; a duplicate category key is caught in phase 3), `unknown-section`, `unknown-category`, `requires-empty-any`, `exclusive-single`, `rename-conflict`, `required` for `categories` when tasks exist, and warning `unused-category`. `id-duplicate`, `unknown-section` and `requires-empty-any` stop before normalization. The others don't.
6. **Normalize** to `Guide` (defaults resolved), plus a `SourceMap` from each section and task ID to its YAML path.
7. **Graph:** `requires-lineage`, then `requires-cycle` (skipped if any lineage error).
8. **Windows:** `end-not-last`, `home-not-leaf`, `until-before-from`, `home-outside-window`, `window-order`.
9. **Markdown body** (`.md` only, runs after phase 4 succeeds, since it needs section IDs): `md-heading`, `md-unknown-section`, `md-duplicate-section`, `walkthrough-twice`, warning `md-preamble`. Body walkthroughs feed normalization.
10. **Prose warnings:** `md-html`, `md-image` over every `walkthrough` and `how`.

### Mapping structural problems to codes

| Situation | Code |
|---|---|
| Key absent | `required` (location: the parent mapping) |
| Plain-text field is `""` | `required` ("must not be empty") |
| Wrong JS type, `sections: []` on a group, `windows: []`, unsupported `requires` shape, literal mismatch | `type` |
| Top-level `sections: []` | `no-leaves` |
| String fails the slug regex or exceeds 64 chars (IDs, category keys, `category`, `exclusive`, `from`, `until`, `home`, `requires` entries, `renamed_from` entries) | `id-format` |
| String longer than its max (§3.3 lengths, §3.7 `walkthrough`/`how`), too many windows / `requires` IDs / `renamed_from` entries, section/task/category counts, nesting depth > 5 | `limit` |
| Unknown key | warning `unknown-key` ("did you mean `x`?" when the Levenshtein distance ≤ 3, else "known keys: …") |
| `overview` > 200 chars or containing `\n` | warning `overview-long` |

The Zod schema uses `z.strictObject` so the generated JSON Schema has `additionalProperties: false` (editors flag typos). The validator turns Zod's `unrecognized_keys` issues into `unknown-key` **warnings**. `sweep` is checked before Zod (phase 3), and Zod issues on `sweep` are dropped.

**Scalars in plain-text fields** (`game`, `title`, `overview`, category `name` and `about`, `walkthrough`, `how`): if YAML resolved a number or boolean, replace it with the scalar's source text before Zod runs (`game: 1942` → `"1942"`).

### Issue locations

| Code | Points at |
|---|---|
| `encoding` | the first invalid byte (line/column of the decoded prefix) |
| `too-large`, `no-root-file` | `null` |
| `yaml-syntax` | the `yaml` library's error position; duplicate key → the second key; custom tag → the tagged node; multiple documents → the start of the second document; alias limit → the first alias node |
| `md-front-matter` | 1:1 |
| `format-version` | the `sweep` value, or the root mapping start when absent |
| `required` | the start of the mapping that lacks the key (the `- ` item or map) |
| `unknown-key` | the key node |
| `id-duplicate` | the second (and later) `id` value; for category keys, the second key |
| `unused-category` | the category key |
| `requires-empty-any` | the empty `any` sequence |
| `requires-cycle` | the `requires` value of the first section in route order on the cycle that has an explicit `requires` (a cycle always has one, because default edges point backward) |
| `requires-lineage`, `unknown-section`, `rename-conflict` | the offending ID scalar |
| `window-order` | `windows[i].from` |
| `until-before-from`, `end-not-last` | the `until` value |
| `md-heading`, `md-unknown-section`, `md-duplicate-section`, `walkthrough-twice` | the body heading line, column 1 |
| `md-preamble` | the first non-blank preamble line, column 1 |
| `md-html`, `md-image` | `.md` body: the exact node position; YAML fields: the field's value node |
| everything else | the value node of the named field |

`path` uses `sections[0].sections[1].requires[0]`, `tasks[3].windows[0].home`, and `categories.loot.name`. For `.md` front matter, add 1 to each line (the opening `---` is line 1). Body issues have `path: null`.

### Normalization

- `title` defaults to `game`. Category `tracked` defaults to `true`. `spoiler` defaults to `false`. `renamed_from` string → `[s]`, absent → `[]`.
- `requires`: list → `{all}`, `{any}` → `{any}`. Omitted on a leaf → `{all: [previous leaf in route order]}` (first leaf `{all: []}`). Omitted on a group → `{all: []}`.
- Window `until` absent → `from`. `home` absent → the first leaf of `from`.
- `walkthrough` and `how`: strip leading blank lines and trailing whitespace. Empty after trimming → `null`. That makes a YAML `|` block (trailing `\n`) and a `.md` body section deep-equal.
- `children` is `[]` for a leaf. `Guide.sections` is the top-level list.
- `MODEL_VERSION` stays `1`. Nothing is stored yet, and the `Window` → `TaskWindow` rename doesn't change the JSON shape.

### Markdown body

- Front matter: line 1 must match `/^---[ \t]*$/`. It closes at the next line matching the same pattern. Otherwise → `md-front-matter`.
- The body is parsed once with `mdast-util-from-markdown` (CommonMark). **Root-level** `heading` nodes with `depth === 1` whose source line matches `/^# ([a-z][a-z0-9]*(?:-[a-z0-9]+)*)[ \t]*$/` are split points. Any other depth-1 heading (setext, extra text, indented, nested in a list or blockquote) → `md-heading`, with the message "level-1 headings must be section IDs; use `##` or deeper inside a walkthrough".
- Section text is the source slice from the line after the heading up to the next split point, trimmed as in Normalization.

### Engine semantics beyond the spec's pseudo-code

- `unlocked` for a group in `SectionView` = some leaf under it is unlocked.
- A pinned locked leaf is current (`state: 'current'`, `unlocked: false`). The UI shows the lock hint from `unlocked`.
- `clearImpact` on an unknown ID, a group, or an already cleared leaf returns `{closing: [], lastChance: [], unlocks: [], wasLocked: false}`. `closing` is in task file order. `unlocks` is in route order.
- `deriveMetrics(guide, progress, run, category?)`: `category` absent or `null` = all tracked categories. A given category that is untracked or unknown gives all zeros.
- `RunSummary.tasksTotal` (runs list) = tracked-category tasks − dont-care − not-chosen, each task counted once. `tasksDone` = tracked tasks that are done.
- A card lists only tracked categories that have at least one row, in category order. Every leaf has a `CardView` entry, possibly with no categories.

### Diff

- Compared fields. Sections: `title`, `overview`, `walkthrough`, `requires`, `spoiler`, `position` (parent ID + index among siblings). Tasks: `title`, `category`, `how`, `windows`, `exclusive`, `spoiler`. Categories: `name`, `about`, `tracked`. `renamedFrom` and `children` are **not** compared (children changes show on the children themselves, as `position`).
- Section and task IDs referenced in the old guide (`requires`, `from`, `until`, `home`, parent in `position`) are translated through the rename map before comparing. Renaming a section therefore doesn't flag every task that points at it.
- Output order: `added` and `edited` follow the new guide's order, `removed` the old guide's, and `renamed` the new guide's.
- The progress diff lists only changes caused by this update. **migrated** = renames whose old ID has usable progress and whose new ID has none. **orphaned** = progress usable under the old guide but not the new one (removed, a leaf became a group, a rename blocked by existing progress under the new ID). **restored** = progress unusable under the old guide but usable under the new one. "Usable": a cleared or pin ID is a leaf, a task-state ID is a task, a tracked ID is a category.

### CLI

- `sweep validate <file> [--json]`. `-h`/`--help` anywhere → usage on stdout, exit 0. `-` → exit 2, "reading from stdin isn't supported; pass a file path". An unknown flag, a wrong file count or an unknown command → usage on stderr, exit 2. An unreadable file or an unsupported extension → message on stderr, exit 2.
- The file resolves against `process.env.INIT_CWD ?? process.cwd()` (done in `main.ts`, and injected as `CliIo.cwd`).
- Text output (stdout), one line per issue: `<file>:<line>:<col> <severity> <code> <message>`, where `<file>` is the argument as given. Issues without a location print `<file> <severity> <code> <message>`. The last line is `<n> error(s), <m> warning(s)` (singular when 1).
- `--json` (stdout): `{"file": <arg>, "errors": n, "warnings": m, "issues": Issue[]}`, with each `issue.file` replaced by the argument. Pretty-printed with 2 spaces.
- Exit 0 with no errors, 1 with errors, 2 for usage.
